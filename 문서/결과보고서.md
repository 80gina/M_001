## 1. 시계열 데이터를 분석하고 요약을 만들어 서비스에서 활용하는 흐름

### 1-1. 무엇을 시계열로 잡았나

제가 진행하던 **제철밥상 플래너** 프로젝트를 이어받아, `(date, value, memo)` 세 필드로 정의했습니다.

- `value` = 그날 '제철 밥상 한 상' 기준 식재료 장바구니의 **kg당 평균 소매가(원)**
- `memo` = 그 시기의 **대표 제철 품목**

19,710건(27품목 × 730일), 2024-09-08 ~ 2026-09-07.

### 1-2. 왜 2년치인가 — 이 과제의 가장 중요한 설계 결정

이 서비스는 값을 **두 축**으로 봅니다.

| 축 | 계산 | 알려주는 것 |
|---|---|---|
| 전주 대비 (단기) | 최근 7일 평균 ÷ 직전 7일 평균 | 지금 오르는 중인가 |
| 평년 대비 (장기) | 최근 7일 평균 ÷ 같은 시기 평년 | 이 시기치고 비싼가 |

**평년을 구하려면 작년 같은 시기의 기록이 있어야 합니다.** 1년 미만이면 비교 대상 자체가 존재하지 않습니다. 그래서 2년(730일)으로 잡았습니다.

축이 둘이어야 하는 이유는 이 표 하나로 설명됩니다.

| 평년 대비 | 전주 대비 | 결론 |
|---|---|---|
| 싸다 | 오르는 중 | **지금 사라** — 반등이 시작됨 |
| 싸다 | 내리는 중 | **기다려도 된다** — 더 내려갈 여지 |
| 비싸다 | 내리는 중 | 조금 기다리면 평년 수준에 닿음 |

축이 하나면 이 네 칸이 구분되지 않습니다.

### 1-3. 평년의 정의

> 평년값 = **같은 달력 시기(월-일 기준 ±7일)의 '다른 해' 값들의 평균**

같은 해의 값은 제외합니다 — 자기 자신과 비교하면 항상 0%가 나오기 때문입니다.

이 근거를 코드에 숨기지 않고 **API 응답과 화면에 그대로 노출**했습니다.

```
2024, 2025, 2026년 자료에서, 최근 7일 각각의 같은 달력 시기 ±7일에
해당하는 다른 해 기록 133건을 평균
```

### 1-4. 요약을 저장하지 않고 조회 시점에 계산하는 이유

원본 레코드는 건드리지 않고, `GET /api/data/summary` 를 호출할 때마다 파생 계산만 합니다.

**저장해두면 데이터를 수정할 때마다 요약도 같이 고쳐야 하고, 그러다 반드시 어긋납니다.** 조회 시 계산하면 데이터가 추가·수정·삭제되는 순간 요약이 자동으로 따라옵니다.

### 1-5. 전체 흐름

```
[시계열 19,710건] ── Firestore data 컬렉션
      │
      ▼
[GET /api/data/summary]
      ├ 기간 · 개수 · 평균/최대/최소 · 표준편차
      ├ 전주 대비 %  (단기 축)
      ├ 평년 대비 %  (장기 축)
      └ 판정 5단계 + 이유 문장
      │
      ▼
[POST /api/chat] 시스템 프롬프트에 삽입 → GPT 호출 → conversations 자동 저장
```

### 📋 1절 요약

| 항목 | 답 |
|---|---|
| 데이터 | 제철 식재료 **품목별** kg당 소매가, 27품목 × 730일 = 19,710건, 2년치 |
| 왜 2년 | 평년 대비를 계산하려면 작년 같은 시기가 있어야 함 |
| 축 두 개 | 전주 대비(단기) + 평년 대비(장기) |
| 평년 정의 | 같은 달력 시기 ±7일의 **다른 해** 값 평균 |
| 요약 저장 | 안 함 — 조회 시 파생 계산 (원본과 어긋나지 않게) |

## 2. FastAPI 프로젝트를 라우터/서비스로 분리한 기준

### 2-1. 나눈 기준

| 계층 | 아는 것 | 모르는 것 |
|---|---|---|
| **라우터** (`app/routers/`) | 경로, HTTP 상태 코드, Pydantic 검증, 예외 → HTTP 변환 | Firestore, OpenAI |
| **서비스** (`app/services/`) | Firestore 접근, 통계 계산, GPT 호출 | HTTP, 요청/응답 |

**판별법 한 줄** — 라우터가 `firebase_admin` 이나 `openai` 를 import 하면 잘못 나뉜 것입니다.

### 2-2. 실제 파일 구성

```
routers/   data.py · conversations.py · chat.py                     (3개)
services/  data_service · summary_service · statistics_service      (7개)
           conversation_service · chat_service · tools · alternatives
```

서비스가 라우터보다 많은 것이 자연스럽습니다. HTTP 경로 하나가 여러 도메인 로직을 쓰기 때문입니다.

### 2-3. 이 구조 덕분에 실제로 얻은 것

`suggest_alternative` 도구를 추가할 때, **라우터를 한 줄도 고치지 않았습니다.** `services/alternatives.py` 를 새로 만들고 `tools.py` 에 등록한 것이 전부입니다. MCP 서버도 같은 `TOOL_SPECS` 를 읽으므로 자동으로 5개가 노출됐습니다.

### 2-4. 경로 선언 순서 — FastAPI의 함정

```python
@router.get("/summary")      # ← 반드시 위
@router.get("/statistics")
@router.get("/export")
@router.get("/{data_id}")    # ← 반드시 아래
```

`/{data_id}` 가 위에 있으면 FastAPI가 `summary` 를 `data_id` 값으로 인식해 404를 냅니다. 이 순서가 깨지지 않도록 스모크 테스트에 검사를 넣었습니다.

### 📋 2절 요약

| 항목 | 답 |
|---|---|
| 기준 | 라우터=HTTP 관심사 / 서비스=도메인 로직 |
| 판별법 | 라우터가 `firebase_admin`·`openai` 를 import 하면 잘못됨 |
| 효과 | 도구 추가 시 라우터 수정 0줄 |
| 주의 | 고정 경로를 `/{변수}` 보다 **위에** 선언 |

## 3. Pydantic을 활용한 요청 데이터 검증

### 3-1. 왜 필요한가

**Firestore는 스키마가 없는 NoSQL입니다.** `{"value": "비쌈"}` 을 보내도 그대로 저장됩니다. 그러면 요약을 계산할 때 문자열과 숫자를 더하려다 서버 전체가 깨집니다.

검증을 DB가 해주지 않으니 **앱 경계에서** 해야 합니다.

### 3-2. 어떻게 했나

```python
class DataCreate(BaseModel):
    date: _date = Field(..., description="측정 날짜 (YYYY-MM-DD)")
    value: float = Field(..., ge=0, le=10_000_000)
    memo: str = Field("", max_length=200)

    @field_validator("memo")
    @classmethod
    def strip_memo(cls, v: str) -> str:
        return v.strip()
```

선언만 하면 FastAPI가 자동으로 `422` 를 돌려줍니다. 라우터 안에 `if` 문을 쓰지 않았습니다.

### 3-3. 이 방식의 장점 세 가지

1. **검증 규칙이 한 곳에 모인다** — 라우터마다 흩어지지 않음
2. **Swagger 문서가 같은 선언에서 자동 생성된다** — 문서와 코드가 어긋날 수 없음
3. **타입이 곧 문서다** — `ge=0, le=10_000_000` 이 그대로 API 명세에 나타남

### 3-4. 실제로 검증이 막은 것

```
POST /api/data  {"date": "날짜아님", "value": -5}
→ 422 Unprocessable Entity
```

이 요청이 통과했다면 Firestore에 `value: -5` 가 저장되고, 평균·최저가 계산이 전부 오염됐을 것입니다.

### 📋 3절 요약

| 항목 | 답 |
|---|---|
| 왜 | Firestore는 스키마가 없어 잘못된 값도 저장됨 |
| 어디서 | 앱 경계 (라우터에 들어오기 전) |
| 어떻게 | Pydantic 모델 선언 → FastAPI가 자동 422 |
| 부수 효과 | Swagger 문서가 같은 선언에서 생성 |

## 4. Firestore에 데이터를 저장하고 CRUD로 다루는 방법

### 4-1. 컬렉션 구조

| 컬렉션 | 문서 형태 |
|---|---|
| `data` | `{date, value, memo, created_at, updated_at}` |
| `conversations` | `{title, messages[], created_at, updated_at}` |

### 4-2. CRUD 대응

| 동작 | Firestore API | 특징 |
|---|---|---|
| 생성 | `collection.add(body)` | **문서 ID 자동 생성** |
| 조회 | `document(id).get()` / `collection.stream()` | `snap.exists` 로 존재 확인 |
| 수정 | `document(id).update(patch)` | 보낸 필드만 병합 |
| 삭제 | `document(id).delete()` | 없는 문서를 지워도 오류가 안 남 → **미리 `.get()` 으로 확인해 404 반환** |

### 4-3. 정렬을 앱에서 하는 이유

Firestore의 `order_by` 는 복합 조건일 때 **색인을 따로 만들어야** 합니다. 이 프로젝트의 데이터 규모(수천 건)에서는 전체를 읽어 파이썬에서 정렬하는 편이 단순하고, 색인 관리 부담이 없습니다.

> 다만 수십만 건 규모가 되면 이 선택은 바뀌어야 합니다. 규모에 따라 답이 달라지는 문제라는 점을 인지하고 선택했습니다.

### 4-4. 개발용 메모리 저장소

`USE_MEMORY_DB=true` 이면 Firestore 대신 **같은 인터페이스를 흉내내는 메모리 저장소**를 씁니다.

```python
class _MemoryCollection:
    def document(self, doc_id=None): ...
    def add(self, payload): ...
    def stream(self): ...
```

덕분에 **Firebase 계정 없이도 120개 테스트를 전부 돌릴 수 있습니다.** 서비스 계층 코드는 어느 쪽이 붙어 있는지 모릅니다.

### 📋 4절 요약

| 항목 | 답 |
|---|---|
| 컬렉션 | `data`, `conversations` 두 개 |
| 생성 | `add()` — ID 자동 생성 |
| 삭제 | 없는 문서도 오류가 없어 `.get()` 으로 먼저 확인 |
| 정렬 | 앱에서 (색인 관리 부담 회피, 규모 전제) |
| 테스트 | 메모리 저장소로 대체해 Firebase 없이 검증 |

## 5. 데이터 요약을 시스템 프롬프트에 주입하는 방식의 원리

### 5-1. 왜 매번 넣어야 하나

**GPT는 상태가 없습니다.** 이전 요청에서 데이터를 보여줬어도 다음 요청에서는 기억하지 못합니다. 그래서 매 요청마다 요약을 `system` 메시지로 **다시** 실어 보냅니다.

```
messages = [
  {"role": "system",    "content": 요약과 판정이 담긴 문장},
  ... 최근 8턴 ...
  {"role": "user",      "content": 사용자 질문},
]
```

### 5-2. 판정을 GPT가 아니라 서버가 내리는 이유

이것이 이 프로젝트의 두 번째 핵심 설계입니다.

| | GPT에게 맡기면 | 서버가 내리면 |
|---|---|---|
| 입력 | "평균 4,624원" | "판정: 평년 수준 / 이유: …" |
| GPT의 일 | 수치 해석 + 판단 + 말투 | **말투만** |
| 위험 | "비싼 편이네요" 를 근거 없이 지어냄 | 판정이 결정적이라 틀릴 수 없음 |

프롬프트에 이렇게 못 박았습니다.

```
[서버가 내린 판정]  ※ 아래 판정과 이유를 그대로 근거로 쓰세요
- 판정: 평년 수준
- 이유: 평년과 비슷합니다. ... 전주 대비로는 -6.2%로 내리는 중입니다.

[답변 규칙]
2. "지금 사도 되나" 류의 질문에는 반드시 [서버가 내린 판정]을 따르세요.
   판정을 뒤집거나 다른 결론을 내리지 마세요. 말투만 자연스럽게 바꾸면 됩니다.
```

이 규칙이 실제로 프롬프트에 실리는지를 스모크 테스트가 검사합니다.

### 5-3. 장점과 한계

| | 내용 |
|---|---|
| **장점** | 토큰이 적게 든다 · 구현이 단순하다 · 원본이 바뀌면 요약이 즉시 따라온다 |
| **한계** | 요약에 **없는 정보는 GPT가 알 수 없다** |

한계의 예 — "6월 중 제일 쌌던 날은?" 은 요약에 없어서 답할 수 없습니다. **이 한계를 보너스①의 Function Calling으로 해결했습니다** (7절).

### 5-4. 토큰 관점

품목이 12개에서 27개로 늘어도 **프롬프트 길이는 품목 수에만 비례**합니다 (한 품목당 한 줄). 레코드가 열 배가 되어도 프롬프트는 그대로입니다. 요약 문장만 들어가기 때문입니다. RAG나 파인튜닝 없이 이 정도로 충분한 이유입니다.

### 📋 5절 요약

| 항목 | 답 |
|---|---|
| 원리 | GPT는 상태가 없으므로 매 요청마다 요약을 system 메시지로 재주입 |
| 핵심 | **판정은 서버가**, GPT는 말투만 — 지어내기 방지 |
| 장점 | 토큰 적음 · 단순함 · 원본과 자동 동기화 |
| 한계 | 요약에 없는 건 모름 → Function Calling으로 보완 |

## 6. 배포 환경에서 CORS / 환경변수 / 키 관리

### 6-1. CORS가 왜 필요한가

프론트는 `*.vercel.app`, 백엔드는 `*.onrender.com` — **출처(origin)가 다릅니다.**

브라우저의 동일 출처 정책은 기본적으로 이런 요청을 차단합니다. 서버가 응답 헤더로 "이 출처는 허용한다"고 알려줘야 통과합니다.

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=settings.ALLOWED_ORIGINS,  # 환경 변수에서 읽음
    ...
)
```

**허용 목록을 코드에 박으면** 배포 주소가 바뀔 때마다 코드를 고쳐 재배포해야 합니다. 그래서 환경 변수로 뺐습니다.

> 실제로 겪을 가장 흔한 사고 — Vercel 배포 후 `ALLOWED_ORIGINS` 에 그 주소를 안 넣으면, **화면은 뜨는데 데이터가 하나도 안 나옵니다.** 브라우저 콘솔에만 CORS 오류가 찍혀서 원인을 찾기 어렵습니다. 그래서 프론트엔드 오류 문구에 이 가능성을 명시했습니다.

### 6-2. 키를 환경 변수로 관리하는 이유

- GitHub은 **공개 저장소의 API 키를 자동으로 스캔**합니다.
- 유출된 OpenAI 키로는 **남이 내 돈으로** 요청을 보낼 수 있습니다.
- 커밋 이력에 한 번 들어가면 나중에 지워도 이력에는 남습니다.

`.gitignore` 에 `.env` 와 `serviceAccountKey.json` 을 넣었고, 코드에는 키 문자열이 **한 개도** 없습니다.

### 6-3. Firebase 키의 특수 문제

서비스 계정 키는 **개행이 포함된 JSON** 입니다. Render 환경 변수 칸에 원문을 붙이면 개행이 깨져 `Invalid JSON` 이 납니다.

그래서 **base64로 인코딩한 한 줄**을 받도록 했습니다.

```bash
base64 -w0 serviceAccountKey.json          # macOS / Linux
[Convert]::ToBase64String([IO.File]::ReadAllBytes("serviceAccountKey.json"))  # Windows
```

세 가지 방식(`_B64`, `_JSON`, 파일 경로)을 우선순위대로 지원해서, 로컬은 파일 경로·배포는 base64로 쓸 수 있게 했습니다.

### 6-4. 콜드스타트 대응

Render 무료 티어는 15분 무접속 시 절전합니다. 첫 요청이 최대 60초 걸립니다.

- 프론트가 페이지 로드 직후 `/health` 를 호출해 **미리 깨웁니다**
- 2.5초 이상 걸리면 상단에 안내 배너를 띄웁니다

| 항목 | 답 |
|---|---|
| CORS | 프론트·백엔드 출처가 달라 브라우저가 차단 → 서버가 허용 헤더를 줘야 함 |
| 왜 환경 변수 | 배포 주소가 바뀔 때 코드를 안 고치려고 |

## 7. [보너스①] 어떤 근거로 어떤 도구를 호출했는가

### 7-1. 왜 도구가 필요했나

5절의 한계 때문입니다. **컨텍스트 주입은 요약에 담긴 것만 답할 수 있습니다.**

### 7-2. 도구 11종과 호출 근거

| 도구 | 호출 근거 | 예시 질문 |
|---|---|---|
| `get_data_summary` | 요약 통계만으로 충분 | "전반적으로 어때?" |
| `query_data` | 특정 기간의 **개별 레코드** 필요 | "지난주 기록 보여줘" |
| `find_extreme` | 기간 내 **극값 탐색** 필요 | "제일 쌌던 날은?" |
| `get_item_verdict` | **한 품목**의 두 축 판정 필요 | "배추 지금 사도 돼?" |
| `browse_by_category` | **갈래**로 훑어야 함 | "수산물 중에 살 만한 거?" |
| `get_item_scores` | 값 말고 **전반적 평가**를 물음 | "지금 시금치 어때?" |
| `get_swot_analysis` | **장보기 계획**의 판단 필요 | "뭘 미루고 뭘 사?" |
| `get_price_forecast` | **앞으로**를 물음 | "김장철 배추값은?" |
| `recommend_dishes` | **뭘 만들지**부터 정해야 함 | "도시락 반찬 추천해줘" |
| `suggest_alternative` | 판정이 나빠 **대안** 필요 | "배추 비싼데 뭘 대신?" |
| `list_past_conversations` | **대화 기록** 조회 필요 | "전에 무슨 얘기 했지?" |

전부 조회 도구였다면 GPT는 첫 번째 것만 반복해서 부릅니다. **판단이 필요한 도구**
(`suggest_alternative`, `get_swot_analysis`, `recommend_dishes`)가 섞여 있어야
"고르는" 행동이 실제로 나타납니다.

스키마(`TOOL_SPECS`)와 구현(`TOOL_IMPLS`)의 키가 **정확히 일치하는지** 스모크 테스트에서
검사합니다. 스키마만 늘리고 구현을 빠뜨리면 GPT가 부른 뒤에야 실패하는데, 그때는
이미 토큰을 쓴 뒤입니다.

### 7-2b. 계산인 것을 예언처럼 말하지 않게 하기

`get_price_forecast` 는 GPT가 가장 단정하기 쉬운 도구라, 시스템 프롬프트에 규칙을
못 박았습니다 (`build_system_prompt` 9~11번).

> "~할 것입니다" 대신 "지금까지의 패턴대로라면 ~쯤으로 계산됩니다"처럼 말하고,
> caveat(작황 급변·명절 수요는 반영 안 됨)를 반드시 함께 전하세요.
> 환율·날씨·운송비는 관측치가 아니라 사용자가 넣은 **가정**입니다.

`get_item_scores` 도 각 축에 `source: measured | reference` 를 실어 보내고
"참고값을 데이터인 것처럼 말하지 말라"고 지시합니다. **모델에게 정직을 부탁하는 대신,
정직할 수밖에 없는 데이터 구조를 넘기는 쪽**을 택했습니다.

### 7-3. 호출 흐름 (실제 동작)

```
사용자: "6월 중에 제일 쌌던 날이 언제야?"
   │
   ▼ POST /api/chat  (system 프롬프트 + tools 스키마 5개)
   │
GPT 1차: finish_reason = "tool_calls"
   └ 근거: 요약에는 '전체 최저가'만 있고 '6월 한정'은 없다
   └ 호출: find_extreme({mode:"min", start:"2026-06-01", end:"2026-06-30"})
   │
   ▼ 서버가 실행 → {found:true, date:"2026-06-10", value:4090, memo:"매실"}
   │  결과를 role:"tool" 메시지로 대화에 추가
   │
GPT 2차: "6월에는 10일이 4,090원/kg으로 가장 저렴했어요. 매실 제철이었네요."
   │
   ▼ 프론트에 호출 추적 표시 + conversations 자동 저장
```

무한 호출 방지를 위해 **최대 3라운드**로 제한했습니다 (`MAX_TOOL_ROUNDS`).

### 7-4. 도메인 지식과 사실을 섞지 않은 설계

`suggest_alternative` 는 두 가지를 **따로** 가져와 합칩니다.

| | 출처 | 예 |
|---|---|---|
| 조리에서 대신할 수 있나 | `alternatives.py` 표 (사람이 적은 지식) | "국거리로 거의 같게 씁니다" |
| 그래서 얼마나 싼가 | 저장된 데이터의 품목별 평균 | "평균 5,029원, 배추보다 26% 비쌈" |

**표에 가격을 적어두면 데이터가 바뀌어도 표는 안 바뀌어 거짓말을 하게 됩니다.** 그래서 표에는 값을 절대 넣지 않고, 이를 테스트로도 막았습니다("표에 `숫자+원` 형태가 없는지").

### 7-5. MCP Server — 멀티채널 검증

같은 5개 도구를 MCP 프로토콜로도 노출했습니다.

```
   OpenAI Function Calling ──┐
                             ├──► TOOL_SPECS / run_tool ──► Firestore
   MCP Server (stdio) ───────┘        (tools.py 한 곳)
```

**정의를 한 곳에만 둔 것이 실제로 효과를 냈습니다.** 도구를 4개→5개로 늘렸을 때 `mcp_server/server.py` 는 **한 줄도 고치지 않았고**, 그대로 5개가 노출됐습니다. 정의가 두 벌이었다면 반드시 어긋났을 것입니다.

## 8. [보너스②] 인사이트·UX 고도화

### 8-1. 확장 통계를 `/summary` 와 분리한 이유

| | 목적 | 지표를 늘리면 |
|---|---|---|
| `/api/data/summary` | AI 프롬프트에 넣을 **짧은** 요약 | 토큰만 먹고 답변 품질 하락 |
| `/api/data/statistics` | 화면에 그릴 **자세한** 지표 | 길어도 됨 |

**목적이 다르면 엔드포인트도 나눈다** — 이 원칙으로 분리했습니다.

제공 지표: 이동평균 7·30일, 요일별 평균, 사분위수, 표준편차, 최장 연속 상승·하락 일수, 품목별 평균.

### 8-1b. 품목 분류 — 대·중·소 3단

`catalog.py` 한 곳에 94품목의 분류·제철 달·조리 성격·민감도를 적고, 화면의 분류 막대와
시세판·그래프 필터가 전부 이 표에서 나옵니다.

두 가지를 지켰습니다.

- **데이터에 있는 품목만** 나무를 만든다 — 카탈로그 전체를 내려주면 가격이 없는 가지를
  눌렀을 때 빈 화면이 나오고, 그건 사용자에게 고장으로 보입니다.
- **대분류를 고르기 전에는 아랫줄을 만들지 않는다** — 3단을 처음부터 다 펼치면
  버튼이 60개가 넘어 오히려 못 찾습니다.

### 8-1c. 조건으로 고르기 — 사용자가 값보다 먼저 정하는 것

사용자는 '배추 2,017원'을 사러 오는 게 아니라 **김치찌개를 하러** 옵니다.
그래서 조리법·목적·계절감·신선도·난이도·편의성을 손잡이로 두고, 음식 82종
(`dishes.py`) 중에서 골라 **그 재료를 지금 값으로 판정해** 돌려줍니다.

점수는 가중합이지만 **조리법·목적만 곱셈 관문**입니다.

```python
gate  = parts["조리법"] * parts["목적"]          # 안 맞으면 0.25배
score = (계절감*1.6 + 난이도*0.9 + 편의성*0.9 + 가격*1.4) * coverage * gate
```

처음엔 전부 가중합이었는데, "국물 요리"를 골랐더니 계절감·가격 점수가 높은 **호박전**이
1위였습니다. 조리법은 취향이 아니라 사용자가 **직접 고른 조건**이므로 관문이 맞습니다.

`dishes.py` 의 표는 대화에서 재료를 뽑는 `mentions.py` 와 **같은 것을 씁니다.** 따로
들고 있으면 한쪽만 고쳐져 "추천은 되는데 대화에서는 못 알아듣는" 어긋남이 생깁니다.

같은 손잡이로 **서버 추천 / AI에게 묻기**를 사용자가 고를 수 있게 했습니다.

| | 좋은 점 | 아쉬운 점 |
|---|---|---|
| 서버 추천 | 같은 조건이면 항상 같은 결과, 판정이 정확 | 말투가 딱딱함 |
| AI에게 묻기 | 사람 말투, 이유 설명이 자연스러움 | 같은 조건이라도 답이 조금씩 다름 |

AI 모드에서도 **값과 판정은 서버 것을 씁니다.** GPT는 조건에 맞는 음식을 고르는
말투만 담당합니다 (5-2절의 원칙을 그대로 확장).

### 8-1d. 시각화 4종 — 측정값과 참고값을 섞지 않기

| 그림 | 답하는 질문 | 근거 |
|---|---|---|
| 평가 지표 레이더 | "값 말고 전반적으로 어때?" | 6축 (측정 3 + 참고 3) |
| SWOT 4칸 | "뭘 지금 사고 뭘 미룰까?" | 지금 값 + 월별 평균 + 변동성 |
| 분류별 히트맵 | "어느 갈래가 언제 싼가?" | 분류 × 12개월 |
| 가격 분포 | "지금이 1년 범위에서 어디쯤?" | 최저~최고 막대 + 현재 점 |

**레이더의 여섯 축은 성격이 두 가지입니다.** 계절성·가격·신선도는 실제 가격에서 계산한
측정값이고, 기호도·편의성·쉬움은 카탈로그에 적어 둔 사람의 판단입니다. 하나로 합친
'종합점수'만 보여주면 틀렸을 때 어디가 틀렸는지 알 수 없습니다. 그래서 응답에
`source: measured | reference` 를 실어 보내고 화면에서 초록 실점과 흰 점으로 나눠 그립니다.

**히트맵은 절대 가격이 아니라 '연평균 대비 그 달 평균'을 칠합니다.** 절대값으로
칠했더니 대하(3만원)가 표 전체를 덮어 채소가 한 칸도 보이지 않았습니다.

**SWOT은 GPT가 아니라 서버가 만듭니다.** 강점·위협은 전부 계산으로 나오기 때문입니다 —
평년보다 싸면 강점, 다음 달 평균이 더 비싸면 위협. 그래서 각 줄에 근거가 붙습니다:
`배추 다음 달 평균이 13% 더 쌉니다 — 미룰수록 유리`.

### 8-1e. 향후 가격 추이선 — 없는 데이터를 있는 척하지 않기

세 가지를 곱해 앞으로 60일을 계산합니다.

```
① 계절 곡선   같은 달력 날짜(±3일)의 다른 해 평균     ← 뼈대
② 수준 보정   최근 14일 실제 ÷ 같은 기간 계절 곡선    ← 올해 수준에서 출발
③ 추세 감쇠   최근 30일 기울기를 절반만, 갈수록 약하게
```

③에 감쇠를 넣은 이유 — 최근 흐름을 그대로 늘렸더니 60일 뒤 값이 터무니없어졌습니다.

**환율·날씨·운송비 데이터는 우리에게 없습니다.** 요구는 있었지만 없는 것을 있는 척할
수는 없었습니다. 대신 **가정값 손잡이**로 뒀습니다 — "환율이 5% 오르면?"을 밀면
품목별 민감도(수산물은 환율 0.30, 산나물은 날씨 0.95)를 곱해 선이 움직입니다.
예언이 아니라 **조건을 넣었을 때의 계산**이고, 화면에도 그대로 적습니다.

선 하나만 그리면 사용자가 그것을 정답으로 읽습니다. 그래서 **평년의 흩어짐으로 만든
띠**를 함께 그리고 예측 구간은 점선으로 표시했습니다. 띠가 넓은 품목은 그만큼 못 믿을
품목이라는 뜻이고, **그 사실이 값 자체만큼 중요합니다.**

### 8-2. 차트를 SVG로 직접 그린 이유

과제가 프레임워크 사용을 금지하므로 차트 라이브러리도 쓰지 않았습니다. canvas가 아닌 **SVG**를 고른 이유는 세 가지입니다.

1. 확대해도 선명하다 (해상도 독립)
2. **색을 CSS 변수로 줄 수 있어 다크 모드가 저절로 따라온다** ← 결정적
3. 각 점이 요소라 마우스 위치를 찾기 쉽다

3개 선(일별/7일/30일) · 체크박스 토글 · 기간 전환(1개월~전체) · 툴팁을 구현했습니다.

### 8-3. CSV 내보내기와 BOM

```
GET /api/data/export?format=csv  →  jecheol_20260907.csv
```

**CSV 앞에 BOM(`﻿`)을 붙였습니다.** 없으면 엑셀이 한글을 CP949로 읽어 `memo` 칸이 전부 깨집니다. (9절 8번 문제와 **같은 원인**입니다.)

### 8-4. 다크 모드 — 3단 정의

```css
:root                                /* 1) 기본 (밝은 화면) */
@media (prefers-color-scheme: dark)  /* 2) OS를 어둡게 써둔 경우 */
:root[data-theme="dark"]             /* 3) 화면에서 직접 고른 경우 */
```

**2번만 있으면 토글이 안 먹고, 3번만 있으면 OS 설정을 무시합니다.** 셋 다 있어야 제대로 동작합니다. 선택은 `localStorage` 에 기억되며, 저장이 막힌 환경(사생활 보호 모드)에서도 깨지지 않도록 `try/catch` 로 감쌌습니다.

### 📋 8절 요약

| 항목 | 답 |
|---|---|
| 통계 분리 | 목적이 다름 — 프롬프트용(짧게) vs 화면용(자세히) |
| 분류 3단 | 데이터에 있는 품목만 · 위 단계를 고르기 전엔 아랫줄을 안 만든다 |
| 조건 추천 | 조리법·목적은 **곱셈 관문** (취향이 아니라 사용자가 고른 조건) |
| 표를 한 곳에 | `dishes.py` 를 추천과 대화가 공유 — 두 벌이면 한쪽만 고쳐진다 |
| 시각화 4종 | 레이더 · SWOT · 히트맵 · 분포 |

| 히트맵 기준 | 절대 가격 아닌 **연평균 대비 %** (안 그러면 비싼 한 품목이 표를 덮음) |
| SWOT 주체 | 서버가 계산 — 강점·위협은 전부 계산으로 나오는 것 |
| 예측선 | 계절 곡선 × 수준 보정 × 감쇠된 추세 + **불확실성 띠** |
| 없는 데이터 | 환율·날씨·운송비는 **가정값 손잡이** — 있는 척하지 않음 |
| SVG 선택 | 선명 · **CSS 변수로 다크모드 자동** · 마우스 처리 쉬움 |
| CSV BOM | 없으면 엑셀에서 한글 깨짐 |
| 다크모드 | 3단 정의 필수 (기본 / OS / 직접 선택) |

## 9. 개발 중 실제로 겪고 해결한 문제

**오류 이력을 숨기지 않고 적습니다.** 겪고 해결한 것 자체가 학습 성과이고, 대부분 테스트가 잡아낸 것들입니다.

| # | 증상 | 원인 | 조치 | 교훈 |
|---|---|---|---|---|
| 1 | 8/31 5,270원 → 9/1 4,180원 (하루 **−21%**) | 월별 계수를 **계단식**으로 적용 | 달 중간값 기준 **선형 보간** | 합성 데이터도 물리적으로 말이 돼야 함 |
| 2 | 평년 대비가 `+0.1%` 라는 이상한 값 | 1번 절벽이 ±7일 창에 걸려 평년값 오염 | 1번을 고치자 `+4.8%` 로 정상화 | 데이터 결함이 지표를 조용히 망가뜨림 |
| 3 | 평년 근거가 "7건"으로 표시 | **날짜 수**를 세고 있었음 (비교값 수가 아님) | 실제 비교값 개수(133건)로 수정 | 화면에 근거를 노출했더니 오류가 드러남 |
| 4 | `pip install` 이 Rust 컴파일에서 실패 | `pydantic-core` 에 Python 3.14용 wheel 없음 | 버전 상향 + **설치 전 dry-run 검증** | 최신 런타임은 패키지가 못 따라올 수 있음 |
| 5 | 422 오류에 파이썬 내부 구조 노출 | "한글이 있으면 신뢰" 규칙이 **입력값의 한글**에 걸림 | `detail` 이 **문자열일 때만** 신뢰 | 휴리스틱은 반드시 새는 구멍이 있음 |
| 6 | 데이터가 1,460건 (**두 배**) | 편의로 넣은 자동 시드가 **테스트에서도 실행** | `SEED_ON_START` 3상태 분리 + 첫 줄 검사 | **켤 수 있게 만들었으면 끌 수 있게도** |
| 7 | 대체재 표 검사 오탐 2건 | `"시원하다"` 의 '원'을 가격으로 오인 | `숫자+원` 형태만 잡도록 정규식 수정 | **테스트 자체도 틀릴 수 있음** |
| 8 | PowerShell 한글이 `?쳥 콘` 으로 깨짐 | `.ps1` 에 UTF-8 BOM 없어 CP949로 읽힘 | BOM 추가 | CSV BOM과 **같은 뿌리**의 문제 |

### 특히 의미 있었던 두 건

**6번** — 로컬 실행을 편하게 하려고 "서버가 뜰 때 데이터 자동 주입"을 넣었더니, 그게 테스트에서도 돌아 데이터가 두 배가 됐습니다. 편의 기능이 검증을 오염시킨 사례입니다. `auto/true/false` 3상태로 나누고, 테스트 **첫 줄**에 "시작 시 0건" 검사를 넣어 다시 생기면 즉시 걸리게 했습니다.

**7번** — 테스트가 빨간 줄 2개를 냈는데, 확인해보니 **하나는 테스트가 틀린 것**(시원하다의 '원')이고 **하나는 진짜 구멍**(바지락이 대체재 표에 없음)이었습니다. 빨간 줄이 떴을 때 "테스트가 이상한가 보다" 하고 넘겼다면 진짜 구멍을 놓쳤을 것입니다.

## 10. 하지 않은 선택과 그 이유

구술 평가에서 "왜 이렇게 안 했나"를 물었을 때의 답입니다.

| 하지 않은 것 | 이유 |
|---|---|
| **RAG / 벡터 DB** | 데이터가 하루 한 줄의 정형 시계열이라 의미 검색이 필요 없음. 요약 주입으로 충분하고 토큰도 훨씬 적게 듦 |
| **파인튜닝** | 답변 형식이 아니라 **데이터**가 매일 바뀜. 파인튜닝은 바뀌는 데이터를 못 따라감 |
| **차트 라이브러리** | 과제가 프레임워크 사용 금지. 또 CSS 변수로 다크모드를 자동 처리하려면 SVG 직접 제어가 유리 |
| **Firestore `order_by`** | 복합 조건에 색인을 따로 만들어야 함. 수천 건 규모에선 앱 정렬이 단순. 단, 수십만 건이면 이 선택은 바뀌어야 함 |
| **판정을 GPT에게 위임** | 근거 없는 답을 지어냄. 판정은 결정적이어야 신뢰할 수 있음 |
| **요약을 DB에 저장** | 원본 수정 시 함께 갱신해야 하고 반드시 어긋남. 조회 시 파생 계산이 안전 |
| **`uvicorn[standard]`** | `uvloop` 에 Python 3.14용 wheel이 없음. 성능 옵션일 뿐 기능 차이 없음 |
| **실측 KAMIS 데이터** | 인증키 발급 전이라 생성 데이터로 진행. **변환 스크립트(`import_kamis.py`)는 미리 만들어 두어** 키가 나오면 한 줄로 교체 가능 |

---

| 환율·날씨·운송비 API 연동 | 정확도는 오르지만 외부 키 2개가 늘고, Render에서 외부 호출이 실패하면 화면이 멈춥니다. **가정값 손잡이**로 두어 사용자가 직접 시나리오를 넣게 했습니다. 근거 없는 숫자를 관측치인 척 보여주는 것보다 정직합니다. |
| 예측에 머신러닝(ARIMA·Prophet 등) | 2년치 일별 데이터로 학습하면 계절 성분만 잡습니다. 그건 지금의 '같은 시기 다른 해 평균'이 이미 하고 있는 일이라, 라이브러리와 학습 시간만 늘고 설명은 어려워집니다. **설명할 수 있는 계산**을 택했습니다. |
| 종합점수 하나로 품목 순위 매기기 | 측정값과 참고값을 한 숫자로 합치면 틀렸을 때 어디가 틀렸는지 알 수 없습니다. 여섯 축을 나눠 보여주고, 어느 축이 측정값인지 표시하는 쪽을 택했습니다. |
| 품목 94개 전부 업로드 | Firestore 무료 요금제는 하루 쓰기 2만 건이 한도입니다. 94품목 × 730일 = 68,620건이라 나흘이 걸립니다. `--profile` 로 규모를 고르게 하고 기본을 한도 안(27품목)에 맞췄습니다. |

## 11. 검증 결과

```
$ USE_MEMORY_DB=true python smoke_test.py
...
🎉 전체 통과   (120개 항목)
```

Firebase도 OpenAI 키도 없이 전 구간을 검증합니다. 검증 범위는 README 13절 표 참고.

특히 **판정 밴드 경계값 11개 케이스**(`-12.0` vs `-11.9` 등)를 하나씩 찍어봤습니다. 구간 나누기는 부등호 하나만 틀려도 티가 안 나게 잘못되기 때문입니다.

**테스트가 실제로 잡아낸 것** — 화면을 넓히면서 품목을 12개에서 27개로 늘렸더니,
스모크 테스트가 곧바로 두 가지를 잡았습니다.

1. 새로 들어온 5품목(고등어·상추·단호박·사과·오징어)이 **대체재 표에 없음**
   → GPT가 "그럼 뭘 대신 쓰지?"에 답할 수 없는 구멍. 5품목을 표에 추가했습니다.
2. `GET /api/tools` 검사가 **도구 개수를 6으로 못 박아** 둬서 깨짐
   → 개수를 세는 대신 **스키마와 구현의 키가 일치하는지**를 검사하도록 바꿨습니다.
     도구를 늘릴 때마다 깨지는 테스트는 곧 주석 처리되기 마련입니다.

두 번째가 더 중요합니다. 테스트가 '숫자가 변했다'가 아니라 **'어긋남이 생겼다'**를
잡아야 오래 살아남습니다.

### 예측·평가가 정직한지 검사하는 항목

새 기능은 값이 맞는지보다 **정직한지**를 검사했습니다.

| 검사 | 무엇을 막나 |
|---|---|
| 예측마다 `low ≤ value ≤ high` | 띠 없는 단일 예측선을 정답처럼 보이게 하는 것 |
| 띠가 갈수록 넓어짐 | 60일 뒤를 내일만큼 확신하는 것 |
| `method`·`caveat` 를 함께 반환 | 계산 근거 없이 숫자만 던지는 것 |
| 가정 없는 호출은 `adjust_pct == 0` | 넣지도 않은 환율 얘기를 꺼내는 것 |
| 축의 `source` 가 measured/reference 둘 다 | 참고값을 데이터로 둔갑시키는 것 |
| 히트맵 값이 ±200% 이내 | 절대 가격을 상대값 자리에 넣는 것 |
| 프롬프트에 "예언이 아니라" 규칙 존재 | 규칙을 지웠는데 아무도 모르는 것 |
