# 제철밥상 플래너 최종 결과보고서

## 1. 프로젝트 배경

제철 식재료는 시기별 가격 차이가 크지만 사용자는 ‘제철’이라는 정보만으로 지금 저렴한지 판단하기 어렵습니다. 가격 서비스, 레시피 검색, 시장 메모, 장바구니 계산도 서로 분리되어 있어 실제 장보기 과정에서 반복 작업이 발생합니다.

## 2. 목표와 사용자

- 일반 가정 사용자가 3분 안에 오늘의 밥상과 살 재료를 결정하도록 지원
- 시장에서 사진·바코드·직접 입력으로 재료를 기록하도록 지원
- 요리교실 강사가 같은 장바구니를 수업 인원과 비용 계획에 활용하도록 확장
- AI가 저장 데이터에 근거해 가격과 구매 시점을 설명하도록 구현

## 3. 설계 결과

### 사용자 화면

따뜻한 크림색·테라코타색을 중심으로 홈, 밥상추천, 시장담기, 장바구니, 강사모드의 다섯 화면을 구성했습니다. 모바일에서는 하단 탭으로 한 손 조작이 가능하고 PC에서도 같은 흐름을 유지합니다.

### 데이터 판정

최근 7일과 직전 7일을 비교하는 단기 축, 최근 7일과 다른 해 같은 시기를 비교하는 장기 축을 함께 사용했습니다. 서버가 다섯 단계 판정과 이유를 계산하므로 AI가 임의로 가격 상태를 해석하지 않습니다.

### AI Agent

Agent는 11개 Function Calling 도구를 통해 가격 기록, 요약, 분류, 제철 품목, 대체재, 음식 재료, 이전 대화 등을 조회합니다. 최대 3라운드 도구 호출 후 답변을 만들고 대화를 자동 저장합니다.

## 4. 구현 결과

| 영역 | 구현 결과 |
|---|---|
| Frontend | 반응형 간편 화면과 고급 데이터 비서 화면 |
| Backend | FastAPI CRUD·요약·통계·추천·채팅·대화 API |
| Data | Firestore 구조, 메모리 대체 저장소, 8,760개 시드 레코드 |
| Market | KAMIS 채소류·축산물·수산물 현재가 라우터 |
| AI | GPT 컨텍스트 주입, 도구 호출, 근거 기반 답변 |
| Memory | 대화 목록·상세·삭제·이어 묻기 |
| User flow | 추천→시장 기록→장바구니→강사 비용 계산 |
| Deployment | Vercel 정적 프론트엔드, Render 호환 백엔드 설정 |

## 5. 검증 결과

1. `node --check frontend/simple.js` 문법 검사 통과
2. `python -m compileall backend/app` 모듈 컴파일 통과
3. 저장소 비밀정보 패턴 검사에서 실제 인증키 없음
4. GitHub에서 README, 실행 화면, 평가 문서, 발표 PPT 확인
5. 사진 후보 선택·바코드 대체 입력·장바구니 합계·강사 비용 흐름 확인

## 6. 팀미션 대응 성과

- 기획·요구사항·소스·발표·데모·결과보고서 제출 구조 완성
- AI Agent, 검색 증강, Long-term Memory, 자동화 워크플로우 적용
- 일반 가정 사용자와 요리교실 강사의 실제 과업을 분리 설계
- 생성형 AI 사용, 사용자 최종 확인, 비밀정보 관리 원칙 명시
- 구현 완료와 후속 고도화 범위를 구분해 평가자가 검증 가능하도록 구성

## 7. 한계

- 사진 기능은 운영형 비전 모델이 아닌 사용자 확인형 후보 프로토타입입니다.
- 바코드는 샘플 카탈로그 기반이며 공공·상용 상품 DB 연결이 필요합니다.
- 영수증은 사진과 합계 입력까지만 지원하고 OCR은 구현하지 않았습니다.
- 실시간 AI·Firestore 기능은 배포 백엔드 환경변수와 서비스 계정 연결이 필요합니다.
- KAMIS 장기 데이터는 운영 전 날짜·단위·중복·결측 재검증이 필요합니다.

## 9. 최종 결론

제철밥상 플래너는 팀미션이 요구하는 생성형 AI 중심 서비스, 핵심 AI 기술 요소, 기능 요구사항, GitHub 문서화, 발표 및 웹 데모 조건에 적합합니다. 현재 버전은 핵심 사용자 흐름과 AI 데이터 비서 구조를 증명하는 제출용 완성본이며, 비전·OCR·인증은 운영 제품으로 확장하기 위한 명확한 다음 단계입니다.
